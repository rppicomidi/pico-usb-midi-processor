# PUMP Processing Architecture Rev 2
## Limitations of PUMP Processing Archutre Rev 1
In Rev 1 of the PUMP Processing Architecture, each USB MIDI packet flowed from a packet source to a packet sink through 0 or more MIDI Processor objects. A packet could be filtered out by not passing it to a MIDI sink. It looked like this:
```
+ ----------- +     + -------------- +     + -------------- +
|             |     |                |     |                |
| MIDI Source + --> + MIDI Processor + --> + MIDI Sink      |
|             |     |  (0 or more)   |     | or drop packet |
+ ----------- +     + -------------- +     + -------------- +
```

Each packet that reached a MIDI sink stayed on the same virtual cable. Each packet was processing in place until it was transmitted. This
architecture enabled a lot of MIDI processor classes, but it made the some features impossible to implement properly. The
following sections discuss the architecture limitations that will be addressed in PUMP Processing Architecture 2.
### Changing the virtual cable
The architecture defined processing chains by virtual cable. If a processor's process() function changed the packet's virtual cable, then the next processing step in the chain from the previous virtual cable should not apply.
### Generating more than one packet from a single input packet
Generating two CC messages from a single pitch bend message is a simple example of generating more than one packet out from a single packet in. More complex examples include re-scaling the 14-bit value from a pair of CC messages or
processing system exclusive messages.
### Generating packets from the MIDI Processor's task() function
Right now, the has_task() function returns false and is not declared virtual because there is no good way for a processor's task() function to generate packets. The architecture only knows how to generate packets out in response to packets in.

## PUMP Processing Architecture Rev 2 Description
The Rev 2 architecture was created to address the limiations of the Rev 1 architecture. The goals are:
- Support multi-packet message generation from both MIDI Processors and task() (or fb_task()) functions.
- Support allowing packets to switch virtual cable, and thus processing chain.
- All packets generated for the same processing chain stay on that chain. That is, they will be passed to the next processor in the chain.
- All packets generated for a new processing chain will be processed from the beginning of the new
chain; that is, as if they were generated by the USB MIDI source.

The new architecture introduces a circular USB MIDI Source Packet Buffer for MIDI IN packets from the
attached MIDI Device and a second circular USB MIDI Source Packet Buffer for MIDI OUT packets from the
USB host. The new architecture also introduces a Processing Chain Packet Buffer in each direction that
organizes packets for the currently processed chain.

The MIDI Processor Manager will pull packets, one at a time, from the appropriate source buffer and
determine the appropriate processing chain. It will then push that packet onto the appropriate Processing Chain Packet
buffer and start processing. Each processor will pull all packets from the Processing Chain Packet Buffer,
process them, and, if the processor output remains on the same processing chain, will push all processing
output back on the Processing Chain Packet Buffer. If the processor generates packets for a different
processing chain, then in will push them on the USB MIDI Source Packet Buffer for processing later.

If a task() function generates packets intended for the attached MIDI device, it will store
them in the MIDI OUT buffer. If it generates packets intended for the host, it will generate them
for the MIDI IN buffer. If the task() function generates a packet that should only be processed
on the processing chain that contains the MIDI processor, and it will store the packet in the processing
chain packet buffer for the chain that contains it. A processor may also have a fb_task() function that
functions just like the task() function except it sends packets in the other direction.
```
+ ----------- +     + --------------- +     + ----------- +     + ---------------- +     + -------------- +
|             |     |                 |     |             |     |                  |     |     Next       |
| MIDI Source + --> + USB MIDI Source + --> + MIDI Packet + --> + Processing Chain + --> + MIDI Processor |
|             |     |  Packet Buffer  |     |             |     |  Packet Buffer   |     | or MIDI Sink   |
+ ----------- +     + ----+-----+---- +     + ----------- +     + --------+------- +     + --+-------+--- +
                          ^     ^                                         ^                  |       |
                          |     |                                         |                  |       |
+ -------------- +        |     |                                         +--- Same chain ---+       |
|                |        |     |                                               processing           |
| MIDI Processor + -------+     |                                                output              |
| task() packets |              |                                                                    |
+ ---------------+              +------------- New processing chain output --------------------------+
```

Each MIDI processor instance, therefore, has a reference two 4 different buffers: the source buffer and the
processing chain packet buffer for the processing the process() function performs, and the source buffer
and the processing chain packet buffer for the processing the feedback() function performs. The task() function
may write to either source buffer or to the Processing Chain Packet Buffer for the process() function. The
fb_task() function may write to either source buffer or to the Processing Chain Packet Buffer for the feedback()
function.

### PUMP Processing Architecture Rev 2 Hazard
Consider processing chain A that contains a MIDI Processor that generates a packet on processing chain B.
Processing chain B must not generate a packet for processing chain A, or else an infinite cycle will
will result. Infinite chains can also result from chain A to chain B to chain C to chain A, etc. The
user will have to be aware that it is possible to create an infinite processing chain and that it is
the user's responsibility to avoid the hazard.

### Possible enhancement
If it is desired to direct output from a processing chain to a packet sink other than one of the USB MIDI ports,
(for example, DIN MIDI or Bluetooth MIDI), it would be possible to assign an unused virtual cable to this new sink. This
would create a new processing chain that would allow additional filtering before output to that new sink. Similarly,
this new chain could support treating DIN MIDI, or Bluetooth MIDI, etc. as a MIDI Source. Supporting this would require
re-thinking the direct one-to-one relationship between virtual cables and processing chains, or it would require limiting
the number of USB virtual cables supported if an alternate MIDI transport device were to be used.

## PUMP Processing Architecture Rev 2 API changes
- The constructor for the MIDI Processor will need a reference to the USB MIDI Source Packet Buffers and to the Processing Chain Packet Buffers. The constructor will assign the appropriate USB MIDI Source Packet Buffer for
re-chained process() and feedback() function outputs, and for the task() function.
- The process() and feeedback() function no longer need a pointer to the packet; it will read packets from the Processing Chain Packet Buffer.
- Each MIDI Processor is responsible for managing packets in the current processing chain packet buffer (depends
on whether the process() or feedback function is called).
- If a MIDI processor can switch processing chain or has a task() function that generates output, then that
processor will need to manage putting data on the appropriate source buffer.
